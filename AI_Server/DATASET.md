# BankScope 합성데이터 설명서

이 데이터는 실제 은행 고객의 방문 기록이 아니라, 개발자가 가정한 고객 상태와 방문 목적을 묶은 PoC용 합성 시나리오다. 외부 학습 데이터셋은 추가하지 않았다. 데이터 정합성·재현성·예외 대응을 확인하는 데 사용하며, 실제 고객의 방문 목적 분포나 금융상품 적합성을 입증하지 않는다.

## 참가서류에 사용할 설명

> BankScope는 개발자가 구성한 합성 금융 업무 시나리오를 활용한다. 업무 예측 데이터는 고객 상태를 표현하는 22개 입력 변수와 22개 업무 유형으로 구성된 11,041건이며, 상품 추천 참조 데이터는 5개 입력 변수와 16개 가상 상품으로 구성된 5,195건이다. 실고객 개인정보를 수집한 데이터셋이나 외부 데이터셋은 사용하지 않았다. 기존 합성 CSV의 논리적 모순과 중복을 정리하고, 동일 고객 상태에서도 다른 방문 목적이 발생하는 예외 시나리오를 추가했다. 원본과 변형 시나리오를 동일 그룹으로 묶어 학습·평가 데이터 간 중복을 방지했으며, 평가 결과는 합성 시나리오에 한정한다. AI의 최초 업무 예상과 직원이 확인한 실제 업무를 분리해 기록하고, 오배정 시 실제 업무를 처리할 수 있는 창구로 이관하는 절차를 구현했다.

공고의 실제 서식 항목에 맞춰 위 내용을 옮겨 사용한다. 이 문서는 대회 주최 측의 합성데이터 허용 여부를 확인한 문서는 아니다.

## 출처와 구성

| 파일 | 용도 | 기존 원본 | 개선 후 |
|---|---|---:|---:|
| `bank_data_1.csv` | Random Forest 업무 예측 | 10,950행 | 11,041행 / 22개 업무 |
| `bank_data_2.csv` | 코사인 유사도 상품 추천 참조 | 5,216행 | 5,195행 / 16개 상품 |
| `data/stress_scenarios.json` | 별도로 작성한 예외 사례 점검 | — | 10개 사례 |

- 원본 CSV는 `data/source/`에 보관했다. 원본을 처음 생성한 코드와 당시 확률·분포 설정은 저장소에서 확인되지 않아, 원본 생성 과정까지 재현 가능하다고 주장하지 않는다.
- 개선 과정은 `prepare_datasets.py`로 재현된다. 버전은 `synthetic-v2`, 난수 시드는 `20260914`다. `data/dataset_manifest.json`에 원본·결과 SHA-256, 행 수, 변경 건수, 클래스별 건수를 기록한다.
- `profile_id`는 입력값으로 만든 그룹 식별자이며 실제 고객 식별자가 아니다. 파생 시나리오가 원본과 같은 그룹을 공유하므로, 파생 행의 입력값 해시와 반드시 같지는 않다.
- 업무 데이터의 `scenario_kind`는 정리된 원본 10,203건, 카드 수령 대기 신호를 추가한 사례 421건, 동일 상태의 다른 방문 목적 417건을 구분한다. 식별자와 시나리오 종류는 모델 입력에서 제외한다.
- 추천 데이터의 `target_product`는 가상 상품명, `product_id`는 앱의 시연용 상품 ID다. 실행 시에는 `product_id`를 추천 정답 열로 사용한다. 실제 가입 성과나 판매 적합성 라벨이 아니다.
- DB의 시연용 고객·구독·완료 이력을 실제 관측 데이터로 간주해 자동 병합하지 않는다. 챗봇의 사이트 가이드·상품 설명은 별도의 응답 참고 자료이며 위 RF 학습 데이터와 구분한다.

## 입력 변수

| 변수 | 의미 / 범위 |
|---|---|
| `age`, `is_corporate`, `gender` | 나이, 법인 여부, 성별 인코딩. 불리언은 0/1. 현재 앱은 MALE을 1, 나머지를 0으로 처리하므로 결측·성별 정보 표현에 한계가 있다. |
| `total_balance`, `account_count` | 계좌 총잔액(원), 계좌 수. 음수는 허용하지 않는다. |
| `has_active_loan`, `has_overdue_loan`, `has_upcoming_payment` | 활성 대출, 연체 대출, 7일 이내 상환 예정 여부 |
| `has_issuing_card`, `has_check_card`, `has_credit_card` | 발급 대기 카드, 체크카드, 신용카드 보유 여부 |
| `has_deposit_sub`, `has_savings_sub` | 예금·적금 보유 여부 |
| `default_risk_level`, `has_business_id` | 법인 위험 단계 0~3, 법인 식별번호 보유 여부. 이 앱의 운영 정의이며 외부 신용평가 점수가 아니다. |
| `recent_deposit_count`, `recent_withdrawal_count`, `recent_transfer_count` | 최근 거래 집계 기간 내 입금·출금·이체 횟수 |
| `days_since_last_tx`, `max_password_fail_count` | 마지막 거래 후 경과 일수(없으면 999), 계좌 중 최대 비밀번호 실패 횟수 |
| `savings_near_maturity`, `deposit_near_maturity` | 90일 이내 적금·예금 만기 여부 |

추천 입력은 `age`, `is_corporate`, `total_balance`, `has_active_loan`, `recent_tx_count`의 5개다. 이름·주민번호·전화번호·계좌번호·실제 사업자번호는 학습 CSV에 포함하지 않는다. 기존 거래 집계 SQL은 1개월 기준이며, 합성 데이터 정리에서는 30일을 사용한다. 달력 월과 30일 경계의 차이는 추후 실증 전에 통일해야 한다.

## 개선 규칙과 남아 있는 가정

계좌가 없으면 잔액을 0으로, 거래 이력 없음은 999일로 정리했다. 마지막 거래가 30일보다 오래됐으면 최근 거래 횟수를 0으로 맞췄다. 상품 없는 만기 표시, 대출 없는 상환 일정, 개인 고객에 붙은 법인 전용 업무도 검증한다. 이번 원본에서는 개인에게 붙은 법인 전용 라벨 76건과 중복 671건을 제외했다. 상품 데이터에서는 앱에 설정된 개인·법인 대상 및 연령 조건과 맞지 않는 21건을 제외했다. 추천 API도 현재 상품의 판매 상태·연령·개인/법인 대상을 확인한다.

업무별로 최대 20개 원본을 선택해 ‘카드 대기 중이어도 다른 업무 방문’, ‘동일 금융 상태에서 다른 방문 목적’ 변형을 추가했다. 변형 비율과 정답은 개발 가정이며 실제 발생 확률이 아니다. 일반적인 방문 사례가 대부분을 차지하는 원본의 편향은 남아 있다. 특히 자산·연령·성별만으로 방문 목적을 확정할 수 없다. 정합성 검사를 통과했다는 사실도 현실성을 보증하지 않는다.

## 평가 방법과 결과

`RF.py`는 그룹 단위로 학습 8,843건과 평가 2,198건을 나눈다. 동일 입력과 원본·변형 그룹이 양쪽에 겹치지 않도록 검사한다. 5회 교차검증은 학습 영역 안에서만 수행한다. 평가 점수에 따라 저장 여부를 결정하던 80% 기준은 제거했으며, 평가에 사용한 학습 영역 모델을 그대로 저장한다.

`data/model_evaluation.json` 기준:

| 합성 데이터 내부 평가 | 결과 |
|---|---:|
| 분리 평가 정확도 | 75.52% |
| Macro F1 | 0.7374 |
| 학습 영역 5회 교차검증 평균 정확도 | 74.92% |
| 최빈 클래스 기준선 정확도 | 8.33% |
| 깊이 5 의사결정나무 기준선 정확도 | 37.40% |
| 학습·평가 동일 입력 중복 | 0건 |
| 별도 예외 사례의 목적 일치 | 5/10건 |

예외 사례 10건은 개발자가 따로 작성한 소규모 점검용이다. 학습 CSV와 같은 입력은 배제했지만, 외부 전문가 검증이나 실제 현장 검증을 거친 자료는 아니다. 최초 무거래 개인 사례가 기존 데이터와 겹쳐, 예측 결과를 보기 전에 나이를 52세로 바꿔 분리했다. 사례별 성공·실패를 모두 보고서에 남기며 실패에 맞춰 정답을 바꾸지 않는다.

보고서의 `minimum_level_sufficient_rate` 92.49%는 예측 업무의 최소 직급이 실제 업무의 최소 직급 이상인지 비교한 대리지표다. 창구의 전문성, 혼잡도, 실제 처리 성공 여부를 측정하지 않으며, 높은 직급으로만 보내도 좋아질 수 있다. **실제 업무 처리 성공률이나 대기시간 감소율로 제시하면 안 된다.** RF의 투표 비율과 SHAP 설명 역시 실제 확률이나 정답의 증거가 아니다. 추천 품질은 아직 별도로 검증하지 않았다.

## 사람이 확인하는 운영 절차

대기 중에는 `업무 수락 / 업무 이관`, 상담 중에는 `업무 이관 / 업무 종료`를 사용한다. 수락 취소는 더보기 메뉴에 있으며 이미 처리한 거래를 되돌리는 동작이 아니다.

이관 시 실제 업무와 사유를 기록하고, 그 업무의 최소 직급을 충족하는 근무 중 직원만 선택할 수 있다. 최초 번호표·접수 시간을 유지하고 해당 창구의 대기열로 이동한다. 현재 상담을 선점하지 않으며 대기시간은 업무별 고정 소요시간을 사용한 추정치다. 이관이 모든 불편을 해결하는 것은 아니므로 반복 이관·총 대기시간·직원 개입량은 향후 실증에서 따로 측정해야 한다.

`predicted_task_detail_type`은 최초 AI 예상, `confirmed_task_detail_type`은 직원 확인 업무다. 이관 기록에는 이전·이후 업무, 담당자, 사유, 시각을 남긴다. 종료할 때 실제 처리 업무를 다시 확인한다. 관리자 재배정만으로는 업무 목적이 확인된 것으로 간주하지 않는다.

기본 학습은 CSV만 사용한다. `--include-confirmed-db`를 명시한 경우에만 ‘종료 + 직원 확인 + 접수 시점 입력 스냅샷’ 조건을 충족한 앱 기록을 추가한다. 과거 완료 이력, AI 예상값만 있는 행, 혼잡도 시연용 `DCG` 이력은 제외한다. 현재 앱에서 만든 테스트 기록도 실고객 데이터는 아니다. 실증 자료의 출처·동의·품질을 확인한 뒤 선별해야 하며, 누적만으로 정확도 향상이 보장되지 않는다.

## 재현

`AI_Server` 폴더에서 가상환경을 활성화한 뒤 실행한다.

```bash
python prepare_datasets.py
python -m unittest test_datasets -v
python RF.py
```

재학습 후 AI 서버를 재시작하면 새 모델을 불러온다. 업무 확인·이관 기능과 입력 스냅샷 저장에는 백엔드의 Flyway V6 적용이 필요하다. 기존 V1~V5 파일을 수정하거나 DB를 초기화할 필요는 없다.
